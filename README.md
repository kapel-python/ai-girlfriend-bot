# Telegram-бот «ИИ девушка»

Бот на Python + aiogram 3.x, который ведёт переписку в личном чате Telegram:
группирует быстрые сообщения (debounce), моделирует человеческое время набора,
поддерживает память, настроение и осторожную проактивность.

## Быстрый старт

```bash
pip install -r requirements.txt
cp .env.example .env       # заполнить BOT_TOKEN и AI_API_KEY
python run.py
```

`.env` не коммитится. В `.env.example` нет секретов; локально база по умолчанию
создаётся как `bot.db` (или по значению `DATABASE_PATH`).

Бот работает только в личных сообщениях. В группе, супергруппе или канале
обычный текст и команды меню получают отказ и не попадают в FSM/сессию
собеседницы.

## Как это работает

```text
Telegram message (private chat)
      ↓
Handler (тонкий)
      ↓
ConversationManager ── буфер сообщений + generation_id
      ↓
Debounce (по умолчанию 2.0 сек, настраивается глобально)
      ↓
AI Service (gptunnel.ru, OpenAI-совместимый API)
      ↓
Response Decision — модель возвращает JSON {should_reply, messages, mood}
      ↓
Typing Simulator — реалистичное время набора текста
      ↓
Telegram Sender — typing-индикатор с keep-alive, отправка
      ↓
История и факты сохраняются в SQLite
```

## Структура

```text
app/
├── bot/
│   ├── handlers/       # menu.py (настройки), chat.py (тонкий handler)
│   ├── keyboards/      # inline-клавиатуры меню
│   ├── middlewares/    # логирование ошибок handlers
│   └── states/         # FSM aiogram
├── ai/
│   ├── client.py       # async-клиент gptunnel (retry, 429/5xx/timeout)
│   ├── prompts.py      # SYSTEM / PERSONALITY / CUSTOM промты, пресеты характера
│   ├── models.py       # список моделей из API с кэшем и fallback
│   └── response_parser.py  # устойчивый парсер JSON-ответа модели
├── conversation/
│   ├── manager.py      # debounce, generation_id, проактивный scheduler
│   ├── memory.py       # краткосрочная + долгосрочная память
│   ├── typing_simulator.py  # модель человеческого времени набора
│   └── sender.py       # typing keep-alive, отправка, нарезка длинных текстов
├── database/
│   ├── database.py     # SQLite (aiosqlite), схема
│   ├── models.py       # dataclass-модели
│   └── repository.py   # весь SQL здесь (легко переехать на PostgreSQL)
├── config.py           # конфигурация из .env
├── logging_config.py   # логи без ключей и содержимого переписки
└── main.py             # сборка зависимостей, polling
```

## Ключевые решения

- **Без HTML-режима по умолчанию**: `Bot` создаётся с `parse_mode=None`.
  Динамические значения меню экранируются перед выводом, а callback_data
  ограничиваются 64 UTF-8 байтами.
- **Нет искусственных задержек перед генерацией** — реализм создаётся на этапе
  отправки: сначала быстрый ответ модели, затем расчёт времени набора.
- **Typing почти сразу**: индикатор «печатает…» запускается сразу после debounce,
  ещё до ответа модели, и держится до отправки — как у человека, который уже
  начал отвечать.
- **Конкурентность**: каждое новое сообщение увеличивает `generation_id` и отменяет
  предыдущую задачу; необработанные сообщения возвращаются в буфер. Устаревший
  ответ никогда не отправляется. Если отправка уже началась — отправленное
  сохраняется в историю, чтобы новая генерация видела контекст.
- **Решение об ответе принимает модель** (JSON `should_reply`), а не `random()`.
  Запрос идёт с `response_format: json_object`; если модель его не поддерживает,
  клиент автоматически откатывается на обычный режим, а длинные не-JSON ответы
  нарезаются на 1–3 логических сообщения.
- **Настроение (mood)**: модель возвращает своё состояние в каждом ответе,
  оно сохраняется в БД и подставляется в промт следующих генераций.
- **Текущий proactive scheduler** не использует старую лестницу эскалации:
  1. после паузы код выбирает широкое время ожидания (log-uniform в диапазоне
     `PROACTIVE_MIN_DELAY_MINUTES`…`PROACTIVE_MAX_DELAY_MINUTES`, по умолчанию
     3–720 минут);
  2. в момент проверки модель делает отдельное `DECISION` (`NO`/`MAYBE`/`YES`),
     а код применяет вероятность с учётом настроения;
  3. только после разрешённого решения код отдельно выбирает время отправки;
     один цикл отправляет не больше одного сообщения.
  После сообщения пользователя цикл начинается заново, есть cooldown и лимит
  `PROACTIVE_MAX_MESSAGES` (по умолчанию 4). Поле `proactive_stage` в БД теперь
  хранит счётчик/bookkeeping, а не фиксированную стадию обиды.
- **Morning и старые stage-настройки deprecated**: `MORNING_*`,
  `PROACTIVE_STAGE1_*`, `PROACTIVE_STAGE2_*`, `PROACTIVE_OFFENSE_*` и старые
  лестницы промтов оставлены для совместимости конфигурации, но текущий
  scheduler их не использует. Отдельного автоматического «доброго утра» нет.
- **Время суток**: в контекст каждой генерации подставляется текущее московское
  время и день недели — ночью она сонная, утром бодрее, выходные отличаются
  от будней. Часовой пояс жёстко Europe/Moscow.
- **Статистика в меню**: «текущие настройки» показывают сообщений в диалоге
  X/100, фактов в памяти, текущее настроение, баланс API (администратору) и
  время у неё.
- **Промты разделены**: системный (не ломается пользователем), пресет характера,
  настроение, пользовательский — хранятся и применяются отдельно.
- **Память**: история хранится в БД полностью, в контекст модели уходят последние
  `SHORT_MEMORY_LIMIT` сообщений (по умолчанию 100). Долгосрочные факты
  извлекаются отдельным LLM-вызовом и ограничены 30 записями. Очистка имеет
  четыре явных варианта: только диалог; диалог + память; только настроение;
  полный сброс (диалог, память, настроение и служебный счётчик).
- **Модель и глобальные параметры**: пункт меню выбора модели, дополнительный
  промт, typing и debounce — глобальные и доступны администратору; они применяются
  ко всем пользователям. `selected_model` в пользовательской записи остаётся
  совместимым default/fallback, но не является отдельным per-user переключателем.
  Характер, custom personality, mood, история и факты — per-user.
- **FSM и destructive-кнопки**: `/help`, `/start`, `/reset`, «назад» и переходы
  меню очищают ожидающее состояние. Ввод имеет TTL; подтверждения очистки и
  удаления характера содержат одноразовый nonce и проверяют FSM state, поэтому
  старая кнопка не удаляет данные. Неизвестные callback безопасно получают
  ответ без выполнения операции.

## Команды

- `/start` — открыть меню настроек
- `/reset` — открыть подтверждение очистки диалога
- `/help` — справка

Других команд бота нет: personality, память, модель и параметры открываются
inline-кнопками. Deep-link для запуска: `https://t.me/SuperAI_girls_ai_bot?start`.

## Docker

После заполнения `.env` запустите:

```bash
docker compose up --build
```

Compose монтирует `./data` в `/app/data` и задаёт контейнеру
`DATABASE_PATH=/app/data/bot.db`, поэтому SQLite не теряется при пересоздании
контейнера. Локальный запуск без Docker использует путь из `.env` (по умолчанию
`bot.db`).

## Сайт

Каталог `site/` — статический лендинг (`index.html`, `styles.css`, `app.js`).
Его можно открыть как `site/index.html` или опубликовать содержимое `site/` на
любом статическом хостинге; отдельный backend для сайта не нужен. Перед
публикацией замените placeholder deep-link на username настоящего бота.
